# dal.wiki "신청/마감형" 캘린더 핸드오프 문서

> **버전:** v0.1 (이데이션 → 구현 핸드오프)
> **작성 맥락:** 글로벌 "정리해봤습니다"류 커뮤니티 기여글 리서치 → 기존 봇이 못 다루는 "능동적 행동 요구(놓치면 끝)" 축 발굴
> **공통 차별점:** 기존 dal.wiki 봇은 전부 "수동적 소비형(발매/방영/관전 — 놓쳐도 나중에 가능)". 이 3종은 "신청/마감형(놓치면 복구 불가)"이라 알림 효용이 질적으로 높음.
> **구현 환경:** Claude Code (이 문서는 핸드오프용, 실제 코딩은 Claude Code에서 진행)

---

## 공통 사항 (3종 봇 모두 적용)

### dal.wiki 플랫폼 규약 (확정)
- **카테고리 태그:** 이벤트명 맨 앞 대괄호 1개가 자동으로 카테고리 태그로 변환됨. 대괄호는 **하나만** 사용.
- **location 필드:** 지리 정보는 전용 `location` 필드 사용 (이벤트명에 박지 말 것).
- **갱신:** PATCH 사용 (과거 DELETE+POST 워크어라운드는 폐기됨).
- **날짜:** `start`/`end`는 ISO 8601. 값이 없으면 `link`/`location` 키는 **통째로 생략**.
- **토픽 ID 조회:** `GET /topics/{encodeURIComponent(name)}` — **dal.wiki 탭에서** 실행 (dev-api는 CORS 막힘).
- **트윗 임베드:** `<div data-dalwiki-tweet-id="ID">`.
- **링크 선호:** 외부 링크에 `target="_blank" rel="noopener noreferrer"` 기본 적용.

### "신청/마감형" 공통 데이터 모델 권장
신청/마감형은 일반 발매 일정과 달리 **두 개의 시점**이 핵심:
- `start` = 마감일시 (D-day의 기준점 — 사용자가 "이때까지 행동해야 함")
- 선택적으로 모집/접수 **시작일**도 의미 있으나, 캘린더 표시 우선순위는 **마감**.

→ 발매형 봇처럼 "출시일 = start" 패턴을 그대로 쓰면 안 됨. **마감일을 start에 넣어** D-day 카운트다운이 자연스럽게 동작하도록 설계.

### 자동 제외 목록 충돌 체크 (확인 완료)
- 3종 모두 기존 제외 목록(피규어 예약 오픈, 소규모 지역 팝업, 편의점 일반 행사, 콘솔 발매, 래플 등)과 **구분되는 결**임을 각 섹션에서 명시.

## 봇 1: 크라우드펀딩 마감 (텀블벅)

### 한 줄 요약
텀블벅에서 **트랙션이 검증된** 서브컬쳐 펀딩 프로젝트의 **마감일**만 큐레이션하는 캘린더.

### 핵심 과제: 트랙션 필터 (= 이 봇의 본질)
텀블벅 전체를 긁으면 노이즈 지옥. 텀블벅이 내장한 "인기 추천(후원자 多)" / "마감 임박(종료 앞둠)" 정렬을 출발점으로, **봇 자체 임계값**으로 컷:

- **달성률 ≥ 300~500%** (이미 흥행 검증) **또는**
- **후원자 수 ≥ N명** (임계값은 카테고리별 튜닝 필요) **+ 마감 D-7 이내**

> 트랙션 필터는 노이즈 제거이자 **품질 보증** 역할 겸함 — 텀블벅 게임 카테고리는 먹튀 비율이 높다는 평이 있어, 트랙션 컷이 사기성 프로젝트를 자연스럽게 걸러줌.

### 카테고리 (토픽 내 카테고리 태그)
텀블벅 자체 분류를 그대로 매핑하되, **dal.wiki 색깔상 서브컬쳐 결만 선별** (전체 다 하면 푸드/테크까지 잡탕됨):
- 권장 포함: 만화·웹툰 / 게임 / 굿즈 / 출판
- 보류: 패션·잡화, 디자인·공예 (수요 보고 추가 판단)
- 제외: 푸드, 여행, 테크 등 비-서브컬쳐

### 데이터 소스 / 수집 방식
- 1차: 텀블벅 인기/마감임박 정렬 페이지
- 수집 시 각 프로젝트의 **달성률·후원자수·마감일시**를 함께 파싱 (필터링 근거)
- API 공개 여부 미확인 → 스크래핑 fallback 필요할 수 있음 (구현 시 확인)

### 이벤트 포맷 (안)
- `start` = 펀딩 마감일시 (D-day 기준)
- 이벤트명: `[게임] OOO 프로젝트 — 달성률 420%` 식 (트랙션을 제목에 노출하면 클릭 유인)
- `link` = 텀블벅 프로젝트 URL

### 제외 목록과의 구분
- 피규어·굿즈 "예약 오픈일"(제외됨)과 다름 → 이건 펀딩 **마감일**.
- 평가: **셋 중 가장 신규 봇답고 엔지니어링 재미 큼.** 우선 구현 추천.

### 미결정 사항 (Open Decisions)
1. 후원자 수 임계값 N의 구체값 (카테고리별 차등?)
2. 와디즈도 포함할지 (와디즈는 테크·생활 비중 높아 서브컬쳐 색 흐려질 수 있음 — 일단 텀블벅 단독 권장)
3. 달성률 컷(300%? 500%?) 최종값
4. 텀블벅 API 존재 여부 / 스크래핑 안정성

## 봇 2: 게임 베타테스트 모집 마감

### 한 줄 요약
화제작의 **CBT/OBT 테스터 모집 마감일**만 좁게 큐레이션. "출시일"이 아니라 "모집 마감일"만 다루는 게 핵심.

### 범위 정의 (가장 중요)
- **좁게 가는 걸 권장:** "화제작 CBT/OBT 모집 마감"만.
- 흔한 사전예약은 모비(mobi.co.kr)가 이미 잘 정리 → **희소성이 차별점**. CBT/OBT만 보면 1~2개월에 1개 수준이지만, 그 하나하나가 임팩트 큼.
- "사전예약 모집"까지 넓히면 항시 수십 개로 양은 충분하나, 흔해서 차별성↓ + 제외 목록(콘솔 출시/MMORPG 패치)과 인접해짐.

### 차별화 포인트 (반드시 명시)
**"출시일이 아니라 모집 마감일만 다룬다"** — 이걸 명확히 해야 메모리상 제외된 "콘솔 게임 발매", "MMORPG 업데이트/패치"와 구분됨.

### 데이터 소스
- 1차: 모비(mobi.co.kr) 사전예약/모집 페이지 — 가장 깔끔
- 보조: 인벤(모집 캘린더 운영 중)
- 큐레이션 단계에서 "화제작" 판단 필요 → Claude Haiku 분류 or 수동 시드 고려

### 이벤트 포맷 (안)
- `start` = 모집 마감일시
- 모집 **시작일**도 의미 있으면 본문/설명에 보조 표기
- 이벤트명: `[게임] OOO CBT 모집 마감` 식

### 인프라 재활용
- 가챠봇 인프라(TweetShift → Discord → Claude Haiku 분류 파이프라인) 일부 재활용 가능.

### 미결정 사항 (Open Decisions)
1. "화제작" 판정 기준 (위시리스트 순위? 화제성 스코어? 수동 큐레이션?)
2. 모집 시작일도 별도 이벤트로 만들지, 마감만 만들지
3. CBT/OBT만 vs 사전예약 모집 일부 포함 (최종 범위)
4. 모비 외 추가 소스 필요 여부

## 봇 3: 식당/팝업 예약 오픈 시각 (기존 팝업봇 확장)

### 한 줄 요약
화제성 팝업/콜라보 카페의 **예약 오픈 시각(D-day)**을 기존 팝업봇에 필드 추가로 확장. **신규 봇 아님.**

### 성격 (다른 둘과의 차이)
- 봇 1·2는 신규 봇, 이건 **기존 팝업/콜라보 카페 봇(TweetShift+웹스크래핑)의 확장**.
- 기존 팝업봇에 **"예약 오픈 D-day" 필드를 추가**하는 방식.
- 예: 헬로키티 50주년 팝업처럼 사전예약 오픈 시각이 명확한 화제성 팝업 대상.

### 범위 한정 (난이도 관리)
- **팝업/콜라보 카페로 좁히는 게 정답.** 오마카세 개별 매장 예약 오픈은 분산도가 너무 높아 비추천.
- 캐치테이블이 일반 식당 예약의 명백한 소스이나:
  - JS 렌더링이라 단순 스크래핑 막힘 → Scrapling/헤드리스 브라우저 필요
  - 개별 매장 분산 → 캘린더화 난이도 높음
- → 일반 식당은 보류, **화제성 팝업의 예약 오픈만** 우선.

### 가치 vs 난이도
- 유저 평가: **난이도 가장 높지만 가치도 가장 큼.**
- 기존 팝업봇이 이미 팝업 일정을 다루므로, "예약 오픈 시각"이라는 **분 단위 긴박성** 필드만 얹으면 차별화 가치 큼 (티켓팅 같은 긴박성).

### 이벤트 포맷 (안)
- 기존 팝업 이벤트에 `예약_오픈` 필드 추가 (별도 이벤트로 분리할지 / 기존 이벤트 내 보조 필드로 둘지 결정 필요)
- `start` = 예약 오픈 일시 (분 단위 정확도 중요)

### 미결정 사항 (Open Decisions)
1. 예약 오픈을 **별도 이벤트**로 만들지, 기존 팝업 이벤트의 **보조 필드**로 둘지
2. 예약 오픈 시각 데이터를 어디서 안정적으로 수집할지 (팝업 주최 SNS? 캐치테이블 부분 활용?)
3. "화제성 팝업" 판정 기준 (기존 팝업봇 큐레이션 기준 재활용?)
4. 캐치테이블 헤드리스 스크래핑까지 갈지, 당분간 SNS 공지 기반으로만 갈지

## 우선순위 제안
1. **봇 1 (텀블벅 펀딩)** — 가장 신규 봇답고 트랙션 필터가 명확한 엔지니어링 과제. 먼저 착수 추천.
2. **봇 2 (베타 모집)** — 가챠봇 인프라 재활용, 범위만 확정하면 빠름.
3. **봇 3 (팝업 예약오픈)** — 기존 봇 확장이라 독립 작업은 아니고, 팝업봇 손볼 때 같이.
